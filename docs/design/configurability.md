# Configurability

Slate components are configurable at four levels. Each level overrides the one before it, and every
platform implements all four with the **same option names and values**.

| # | Level | Scope | Web | Blazor | WPF / Avalonia |
|---|---|---|---|---|---|
| 1 | **Theme** | App or subtree | `createTheme(options)` + `applyTheme(el, theme)`, or `<sl-provider .themeOptions>` | `AddSlate(o => o.Theme = …)` / `<SlateProvider ThemeOptions="…">` | `SlateTheme.Options = …` / `SlateTheme.Apply(definition)` |
| 2 | **Component tokens** | App or subtree | `--sl-component-*` CSS variables | same CSS variables (`Style` or a stylesheet) | `Sl.Component.*` resources (override in any ResourceDictionary scope) |
| 3 | **Defaults** | App | `configureDefaults({...})` | `AddSlate(o => o.Defaults.Button.Size = …)` | `SlateTheme.Defaults` / `AddSlate(o => o.Defaults…)` |
| 4 | **Parameters** | One instance | attributes/properties | `[Parameter]`s | properties / `sl:Sl.*` attached properties |

Plus **scoped mode switches** usable on any subtree: theme mode (`light | dark | system`), density
(`compact | comfortable`) — web/Blazor via `data-sl-theme` / `data-sl-density` (or a nested provider),
XAML via inheritable `sl:Sl.Density` and theme scope.

## 1. Themes (Slate.Core `ThemeBuilder`)

```csharp
var acme = ThemeBuilder.Build(new SlateThemeOptions {
    Name = "acme", Base = ThemeNames.Dark,
    Accent = "#FF5A1F",          // brand colour → accent default/hover/pressed/subtle/text/link + on-accent text
    RadiusScale = 1.5,           // 0 = square … 1 = Alloy … 1.5 = softer
    FontFamily = "Inter, sans-serif",
    Overrides = { ["color.background.canvas"] = "#0B0B0F", ["component.card.radius"] = "16px" },
});
```

- The accent is adjusted **in lightness only**, as little as needed, so every rule still holds: on-accent
  text ≥ 4.5:1 on all states, accent fill ≥ 3:1 on every surface, accent text/links ≥ 4.5:1 on every reading
  surface. Tested for 80 brand colours in both bases.
- Changes propagate through component-token aliases (a new accent restyles `component.selection.checked`;
  `RadiusScale` reaches `component.button.radius`) unless a component token is overridden explicitly.
- The TypeScript port in `@slate/web` must produce byte-identical values: `tests/fixtures/theme-builder.json`
  is generated by Slate.Core's tests and asserted by the web tests.
- Platforms apply `SlateThemeDefinition.Values` (path → CSS value) using the standard names: CSS
  `--sl-<path>`, XAML `Sl.<Path>` (+ `Sl.Brush.*` for semantic colours, `.Brush`/`.Corner`/`.Thickness`/`.Effect`
  suffixes for component tokens). Only `ChangedPaths` need writing.

## 2. Component tokens (`design/tokens/components/components.json`)

Per-component knobs (`component.button.radius`, `component.field.background`, `component.card.padding`,
`component.dialog.radius`, `component.snackbar.background`, …). Each defaults to an alias of a foundation or
semantic token. Components must read **only** their component tokens for these properties (never the
underlying token directly), so overriding one restyles that component everywhere it appears in scope.

## 3. Defaults (`SlateDefaults` in Slate.Core)

App-wide defaults for options a team wants to change globally: `Button` (Variant, Tone, Size, Radius),
`Field` (Variant, Size, Radius), `Card` (Variant, Radius), `Selection` (LabelPlacement), `Dialog`
(`DialogOptions`), `Snackbar` (`SnackbarConfiguration`). A parameter set on a component always wins over a
default; an unset parameter reads the default **at render time** (changing defaults later affects
components rendered afterwards).

## 4. Parameters — the canonical API

`design/api/components.json` is the source of truth for every component's options, value sets, slots,
events and styling parts. Each platform has a conformance test that loads it and fails when an option is
missing or misspelled.

### Spelling

| Concept | Canonical | Web | Blazor | WPF / Avalonia |
|---|---|---|---|---|
| Option | `StartIcon` | property `startIcon`, attribute `start-icon` | `StartIcon` | `StartIcon` property, or `sl:Sl.StartIcon` on native controls |
| Enum value | `ButtonVariant.Solid` | `"solid"` | `ButtonVariant.Solid` | `Solid` |
| Flag | `Loading` | `loading` (boolean attribute) | `Loading` | `Loading` — no `Is` prefix, except framework-native ones (`IsEnabled`, `IsChecked`, `IsReadOnly`) on native controls |
| Slot | `HeaderActions` | `<x slot="header-actions">` | `RenderFragment HeaderActions` | `HeaderActions` (object/content property) |
| Event | `Dismissed` | `sl-dismissed` CustomEvent | `EventCallback Dismissed` | `Dismissed` routed/CLR event |

Attached properties for native controls live on a class named `Sl` on **both** XAML platforms
(`sl:Sl.Variant`, `sl:Sl.Tone`, …).

### Colour vocabulary

- `Tone` (`neutral accent success warning danger info`) colours a component.
- `Severity` (`normal info success warning error`) describes a *message* (Alert, snackbar, message box) and maps
  to a tone (`error → danger`).
- Buttons combine `Variant × Tone`: the primary action is `Solid + Accent`; a destructive confirm is
  `Solid + Danger`; a quiet destructive action is `Outlined + Danger`.

### Styling hooks (every component)

- **Web:** host `class`/`style`; `::part(...)` for each part listed in components.json (parts of nested
  components are re-exported with `exportparts`); component CSS variables.
- **Blazor:** `Class`, `Style`, `AdditionalAttributes` (splatted onto the root element); part-level
  `*Class` parameters only where a part is commonly restyled.
- **XAML:** native `Classes`/`Style`/`Theme`, `PART_*` names for template parts, and `Sl.Component.*` resources.

## Rules for adding an option

1. Add it to `design/api/components.json` (name, kind, type, default) and to this document if it introduces a concept.
2. Implement it on every platform — or list the exceptions in `platforms`.
3. If it changes appearance, drive it through a component token, not a hard-coded value.
4. Conformance tests then pass on each platform.
